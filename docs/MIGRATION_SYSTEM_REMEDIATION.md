# Migration System Remediation Plan

## Current State (2025-10-30)

### Overview
The AthleteMetrics project has a **hybrid migration system** that is causing issues with applying new migrations in CI/CD:

- **Drizzle-generated migrations**: 1 migration (0000) with snapshot file
- **Manual SQL migrations**: 21 migrations (0001-0021) without snapshot files
- **Applied to staging/production**: Migrations 0000-0013
- **Pending migrations**: 0014-0021 (cannot be applied via drizzle)

### Architecture Issue

Drizzle's `migrate()` function requires **both** files for each migration:
1. **SQL file**: `migrations/0014_add_organization_soft_delete_indexes.sql` ✅ EXISTS
2. **Snapshot file**: `migrations/meta/0014_snapshot.json` ❌ MISSING

Without snapshots, Drizzle silently skips migrations during `npm run db:migrate`.

### Impact

- ✅ CI passes after fix (minMigrationCount set to 13)
- ⚠️ Migrations 0014-0021 are defined but not applied
- ⚠️ Future schema changes in those migrations won't reach staging/production
- ⚠️ Schema drift between environments is possible

## Affected Migrations

Migrations that cannot be applied via drizzle (missing snapshots):

| Migration | Description | Risk Level |
|-----------|-------------|------------|
| 0014 | Add organization soft delete indexes | Low - Performance optimization |
| 0015 | Add measurements.organization_id column | **HIGH** - Data model change |
| 0016 | Add measurements table indexes | Medium - Performance optimization |
| 0017 | Add composite analytics indexes | Medium - Performance optimization |
| 0018 | Add org query composite indexes | Medium - Performance optimization |
| 0019 | Add user_teams temporal index | Low - Performance optimization |
| 0020 | Add measurements org/metric analytics index | Medium - Performance optimization |
| 0021 | Backfill measurements.organization_id | **HIGH** - Data migration |

**CRITICAL**: Migrations 0015 and 0021 are essential for multi-tenancy:
- 0015 adds the `organization_id` column to measurements
- 0021 backfills existing data with organization_id values

## Remediation Options

### Option 1: Generate Snapshot Files (Recommended)

**Approach**: Generate snapshot JSON files for migrations 0014-0021 to make them drizzle-compatible.

**Pros**:
- Maintains consistency with drizzle migration system
- Allows using `npm run db:migrate` for all migrations
- Snapshots provide rollback capability

**Cons**:
- Complex for already-applied migrations (0014-0021 SQL exists)
- Requires careful manual snapshot creation

**Implementation Steps**:
1. For each migration 0014-0021, create a snapshot JSON file in `migrations/meta/`
2. Snapshots should match the schema state after the migration SQL runs
3. Test snapshots by applying to a fresh database
4. Update CI to verify all migrations have snapshots

**Effort**: Medium (4-8 hours)

### Option 2: Separate Manual Migration System

**Approach**: Keep migrations 0014-0021 as pure SQL and apply them outside of drizzle.

**Pros**:
- Simpler - no need to reverse-engineer snapshots
- More explicit control over SQL execution
- Easier to understand for developers

**Cons**:
- Two migration systems to maintain
- More complex CI/CD workflow

**Implementation Steps**:
1. Create `scripts/apply-manual-migrations.js` to run migrations 0014-0021
2. Update CI workflow to run manual migrations after drizzle migrations
3. Add tracking mechanism for manual migrations
4. Update documentation

**Effort**: Low (2-4 hours)

### Option 3: Regenerate Migration History

**Approach**: Start fresh with a new drizzle migration history.

**Pros**:
- Clean slate - all migrations properly generated by drizzle
- Consistent migration system going forward

**Cons**:
- **HIGH RISK** - requires careful production migration
- Existing databases need special handling
- Significant testing required

**Implementation Steps**:
1. Export production schema to SQL
2. Create new migration 0000 with drizzle-kit generate
3. Create migration plan for production databases
4. Extensive testing in staging before production

**Effort**: High (8-16 hours)

## Recommended Approach: Option 2 (Separate Manual Migration System)

Given the current state and risk profile, **Option 2** is recommended because:

1. **Low Risk**: Doesn't touch existing migration system
2. **Quick Fix**: Can be implemented and tested rapidly
3. **Explicit**: Makes the dual-system nature clear to developers
4. **Pragmatic**: Acknowledges the current architecture rather than fighting it

## Implementation Plan (Option 2)

### Phase 1: Create Manual Migration Script (30 min)

```javascript
// scripts/apply-manual-migrations.js
#!/usr/bin/env node

/**
 * Apply manual SQL migrations that don't have drizzle snapshots
 * These migrations are tracked separately from drizzle's system
 */

import postgres from 'postgres';
import { readFileSync, readdirSync } from 'fs';
import { join, dirname } from 'path';
import { fileURLToPath } from 'url';

const __filename = fileURLToPath(import.meta.url);
const __dirname = dirname(__filename);

// Migrations to apply (in order)
const MANUAL_MIGRATIONS = [
  '0014_add_organization_soft_delete_indexes',
  '0015_add_measurements_organization_columns',
  '0016_add_measurements_table_indexes',
  '0017_add_composite_analytics_indexes',
  '0018_add_org_query_composite_indexes',
  '0019_add_user_teams_temporal_index',
  '0020_add_measurements_org_metric_analytics_index',
  '0021_backfill_measurements_org_from_users',
];

async function applyManualMigrations() {
  const DATABASE_URL = process.env.DATABASE_URL;

  if (!DATABASE_URL) {
    console.error('❌ DATABASE_URL required');
    process.exit(1);
  }

  const sql = postgres(DATABASE_URL, {
    max: 1,
    ssl: DATABASE_URL.includes('localhost') ? false : 'require'
  });

  try {
    console.log('🔄 Applying manual SQL migrations...\n');

    // Create tracking table for manual migrations
    await sql.unsafe(`
      CREATE TABLE IF NOT EXISTS manual_migrations (
        id SERIAL PRIMARY KEY,
        migration_name TEXT NOT NULL UNIQUE,
        applied_at TIMESTAMP DEFAULT NOW()
      )
    `);

    // Check which migrations are already applied
    const applied = await sql.unsafe(`
      SELECT migration_name FROM manual_migrations
    `);
    const appliedNames = new Set(applied.map(r => r.migration_name));

    // Apply each migration
    for (const migrationName of MANUAL_MIGRATIONS) {
      if (appliedNames.has(migrationName)) {
        console.log(`⏭️  ${migrationName} (already applied)`);
        continue;
      }

      console.log(`🔄 Applying ${migrationName}...`);

      const sqlFile = join(__dirname, '..', 'migrations', `${migrationName}.sql`);
      const migrationSQL = readFileSync(sqlFile, 'utf8');

      await sql.begin(async sql => {
        await sql.unsafe(migrationSQL);
        await sql.unsafe(`
          INSERT INTO manual_migrations (migration_name)
          VALUES ($1)
        `, [migrationName]);
      });

      console.log(`✅ ${migrationName} applied\n`);
    }

    console.log('✅ All manual migrations applied successfully\n');
    process.exit(0);
  } catch (error) {
    console.error('\n❌ Manual migration failed\n');
    console.error(`Error: ${error.message}`);
    console.error(`\nStack: ${error.stack}`);
    process.exit(1);
  } finally {
    await sql.end();
  }
}

applyManualMigrations();
```

### Phase 2: Update CI Workflow (15 min)

Add manual migration step after drizzle migrations:

```yaml
- name: Run database migrations
  run: |
    echo "🔄 Running drizzle migrations..."
    npm run db:migrate
    echo "🔄 Running manual SQL migrations..."
    node scripts/apply-manual-migrations.js
  env:
    DATABASE_URL: ${{ secrets.RAILWAY_STAGING_PUBLIC_DATABASE_URL }}
```

### Phase 3: Update package.json (5 min)

```json

  }

```

### Phase 5: Update Documentation (15 min)

Update CLAUDE.md and README with new migration workflow:

```markdown
## Database Migrations

This project uses a **dual migration system**:

1. **Drizzle migrations** (0000-0013): Applied via `npm run db:migrate`
2. **Manual SQL migrations** (0014-0021): Applied via `npm run db:migrate:manual`

To apply all migrations: `npm run db:migrate:all`

### Why Two Systems?

Migrations 0014-0021 were created without drizzle snapshot files, so they
cannot be applied by drizzle's migrate() function. Rather than regenerate
the entire migration history (high risk), we maintain them as manual SQL.
```

## Rollback Plan

If manual migrations fail:

1. **Immediate**: Revert CI workflow changes
2. **Data safety**: Manual migrations use transactions - failed migrations auto-rollback
3. **Recovery**: Restore database from backup (taken before migrations)
4. **Fix**: Debug migration SQL, fix, and re-run

## Future Considerations

Once manual migrations are stable, consider:

1. **Consolidation**: Merge manual migrations into drizzle by generating snapshots
2. **New migrations**: All future migrations should be drizzle-generated
3. **Tooling**: Create utility to verify snapshot/SQL file pairs exist
