# ADR-002: Eval Report v2 (saved eval reports)

**Date**: 2026-10-09
**Status**: Accepted

Implements AM-FEAT-019 (branches `feature/eval-report-p1-domain` through `feature/eval-report-p6-docs`; migration 0153, number provisional). Operator and developer guide: `docs/EVAL_REPORT.md`. Open items: `docs/EVAL_REPORT_FOLLOWUPS.md`.

Stack note: P3d (COPPA retention) and P4 (#560, the all-report-types under-13 share guard) are part of this stack.

## Context

After an evaluation event a coach needs a family-facing report: only that event's numbers, the athlete's age-group comparison, a plain-language "Fresh & Healthy" read and a coach note. The platform already had a report system (`reports`, `report_snapshots`, `report_shares`, public links, "my reports", PDF export), but its individual report reads an athlete's history over a timeframe, computes age as of today, and falls through to the individual generator for any unknown report type. An earlier branch (`feature/eval-report-onepager`, superseded) used best-ever values, dated the report today, defaulted a missing gender to Female and compared everyone with D1; only its gauge and header drawing was reused (commit `244c53f8`). The data is about minors, so access and COPPA behavior mattered as much as layout.

## Decision

1. **Eval reports are saved `reports` rows with `reportType = 'eval'`.** Every generation inserts a new row (`POST /api/events/:eventId/athletes/:athleteId/eval-report` in `packages/api/routes/event-report-routes.ts`). `config` is validated by `evalReportConfigSchema` (`packages/shared/eval-report-config.ts`) and holds `eventId`, `athleteId`, `metrics`, `selection`, `load`, `coachNote`, the overrides and the frozen `model` (the `EvalReportModel`). Snapshots, share links, the athlete "my reports" view and the PDF routes are reused rather than rebuilt. The renderer draws only the frozen model, so a report always shows what was generated, even if the event is corrected later. Reusing the table meant closing every route that touches reports, because existing checks only test organization membership and an athlete account is a member:
   - `canAccessEvalRow` (`packages/api/routes/eval-report-access.ts`) allows an eval row only for coach, org admin or site admin **in the report row's own organization** (`getOrgRole(user, report.organizationId)` and `isMeasurementWriterRole`), never the session role. It is applied to list filtering (`GET /api/reports`), get, update, delete, pin, unpin, archive, unarchive, generate, snapshot list and delete, PDF (GET and POST), insights, share, share-bulk, bulk-distribute, bulk archive/unarchive/delete (`hasInaccessibleEval`), share listing and share revoke. Snapshot creation (`POST /api/reports/:id/snapshots`) uses an inline equivalent.
   - A caller who fails the gate gets **404**, not 403, so the response does not reveal that the id is an eval.
   - `config` is immutable: `PUT /api/reports/:id` for an eval accepts only `name` and `description` (`evalReportUpdateSchema`).
   - Eval rows are rejected by `generate-insights`, `PATCH insights` (400) and `share-bulk` (400); `/share` must name `config.athleteId`; `bulk-distribute` includes eval rows.
   - `GET /api/reports` strips the heavy model from eval rows (`stripEvalModel`).
   - Rule for future work: **any new route that touches reports must gate eval rows with `canAccessEvalRow`.** The athlete reaches their own eval only through `/api/my/reports/:shareId`.
2. **Data scope is event, athlete, organization and verified only.** `loadEvalReportInputs` (`packages/api/services/eval-report-service.ts`) reads `measurements` with `eventId`, `userId`, `organizationId` and `isVerified = true`; `eventBests` re-applies the same scope and picks the best per metric honoring `lower_is_better`. The report date is `eventCalendarDate(event)`, not today, and the athlete's age is taken at that date. Derived values (5-0-5 LSI, single-leg CMJ asymmetry, EUR, COD deficit, the headline 5-0-5) are recomputed from the event's per-leg bests by `recomputeDerived`; a stored derived total is replaced, or dropped when an input is missing. The retest trend uses the latest earlier event of the same athlete and organization and only when both events used the same metric code and unit (`selectPriorEvent`, `retestTrend`). `resolveEvalTarget` answers 404 unless the athlete has a verified measurement in the event.
3. **Strict age-group matching; no tier names.** `matchTierGroup` (`eval-report/tier-match.ts`) requires age at the event date between 11 and 18, sex exactly `Male` or `Female`, a sport and metric code that match exactly, and a set carrying both age bounds (explicit null checks, so `ageMin = 0` is a real bound). Anything else returns null and the report shows value and unit with no gauge. The seeded age-group sets are **single "Average" rows, not tier ladders**, so the comparison is above or below the age-group average (`AverageComparison`), drawn as a bar with the average tick at the centre. A genuine multi-tier group (rows with a tier group and order) still goes through `selectTierGroup` and `evaluateTierBenchmark`, but the PDF prints no tier name either way. `NO_TIER_CODES` never compares EUR, momentum, COD deficit, `RSI_105`, T-test, single-leg CMJ and the LSI codes. LSI is shown only as Balance wording (`balanceLine`: 95 and above Balanced, 90 to under 95 Keep an eye on it, under 90 or a left-right gap over 0.15 s Worth working on; omitted unless both legs were tested; a neutral label when no LSI set exists for the athlete's sex). The college standard (`matchCollegeStandard`) is a secondary gauge from the D1 "Average" row, found by name (`/average/i`), so it depends on seed naming. Males get value only until AM-FEAT-020 adds male sets. The existing applicability filters in `benchmark-service.ts` and `report-service.ts` were deliberately not reused (age as of today, filters skipped on null age or gender, truthy checks).
4. **Logical keys, not metric codes, in saved selections and templates.** `EVAL_METRIC_CODES` (`eval-report/metric-key-map.ts`) maps keys such as `505_LEFT` to protocol-aware codes (`AGILITY_505_YD_L`); `TEMPLATE_METRIC_CODES` (`eval-report/template-keys.ts`) extends it with battery-only keys (`BODY_HEIGHT`, `PATTERN_*`, `TRANSITION_*`, ...). A code rename changes one map. A yard key never maps to a meter code. Limits: a key outside the map is treated as a literal `site_metrics` code (a coach-saved custom code), so a rename of such a code is not covered; `keyForCode` throws if a code is spelled like a different logical key. `metric-key-map.test.ts` checks mapped codes against the `INSERT INTO site_metrics` statements in `migrations/`, with an explicit exception list for codes the spec names that no seed creates yet. Migration 0153 seeds the global template "Soccer eval (yards)" and **skips any code missing from `site_metrics`** (it still lists skipped keys in its NOTICE; an inactive row counts as missing). The body keys resolve to the real codes `BODY_HEIGHT` -> `HEIGHT_IN` and `BODY_WEIGHT` -> `WEIGHT_LBS` (staging and production `site_metrics` contain both; `HEIGHT` and `WEIGHT` exist on neither). `RSI_105`, `JUMP_CMJ_SL_L` and `JUMP_CMJ_SL_R` existed on neither environment, so the first seed omits them; migration 0156 later creates them (copied from `RSI` and `JUMP_CMJ_HOH`) and tops up the global template (`RSI_BILATERAL` required, the single-leg CMJ sides optional). `JUMP_CMJ_SL_ASYM` remains the only mapped code with no seed. Production is at migration 0143, so 0144-0153 apply in one boot, which creates `AGILITY_505_YD_L/R`, the `MQ_*` codes and `MOMENTUM` before 0153 seeds; applying a template to an event also skips and reports missing codes. Migration number 0153 is provisional: 0151 is taken twice (the yard-benchmark description rewrite and the unmerged AM-FEAT-018 momentum branch), so the next free number must be taken at merge (`docs/MIGRATION_SYSTEM_REMEDIATION.md`).
5. **Preset rules** (`resolvePreset` in `eval-report/selection.ts`): graduation year first, then age, else High school. The school year rolls over on **Aug 1**, judged at the event date. Years to graduation: 0 or less is Senior; 1 is Senior from **June 1** (rising senior) until Aug 1, otherwise High school; 2 to 3 is High school; **4 or more is Middle school** (grade 8 or below). With no graduation year: age 17 and over Senior, 14 to 16 High school, otherwise Middle school. Defaults: Middle school hides the college gauge and puts the note first; Senior shows the college gauge; the gauge is hidden under age 14 unless the coach turns it on (`showCollegeGauge`). Retest trend and Fresh & Healthy default on for all three.
6. **Privacy by construction.** The model builder takes no survey inputs and reads no wellness tables. Two guards: `eval-report/model-guard.ts` fails `tsc` if any property name in the `EvalReportModel` type graph contains a survey or wellness word; `evalReportConfigSchema` rejects a frozen model with such a key at any depth (`hasWellnessKey`). MQI appears only as a band word (`movementBand`, shared constant `MQI_BANDS` in `packages/shared/mqi-band.ts`; 0-8 Developing, 9-14 Competent, 15-19 Efficient, 20-24 Advanced); the raw score and the per-pattern scores never reach the model. The event's own MQI is used, not the latest across events. Load is the coach's light/medium/heavy pick, nothing is calculated, and the line is omitted if unset. Template text avoids injury and medical wording (`copy.ts` is covered by a copy lint test); the coach note is free text and unchecked (control characters stripped, 2000 characters).
7. **COPPA** (P3c, P3d and P4).
   - Snapshot flag: `createSnapshot` in `packages/api/services/report-service.ts` has an eval arm that snapshots the frozen model as `{ reportType: 'eval', model, orgBranding }` and sets the minor flag from `isEvalSnapshotRestricted`: restricted when `users.isMinor` is true, there is no usable birth date, the event date is unparseable, the athlete was under 13 at the **event date** (`wasUnder13At`), or any error occurs (fail closed).
   - Opening a restricted eval snapshot: `enforcePublicSnapshotAccess` is unchanged for logged-out viewers (403). For eval rows, `canOpenRestrictedEval` admits a site admin, a coach or org admin of the report's organization, the athlete, or a parent with an active `parentAthleteLinks` row **for that athlete**. The generic check (a parent of any athlete in the org) is bypassed for eval rows.
   - Share to athlete (**John, 2026-10-09: blocked for under-13 only**): `/share`, `/share-bulk` and `/bulk-distribute` apply P4's generic guard to every report type, using `isUnder13OrUnknownDob` (`packages/shared/coppa-utils.ts`) on the athlete's **current** age; a missing, unparseable or future birth date also blocks (fail closed). `/share` answers 403 `UNDER_13_SHARE_BLOCKED`; the bulk routes skip with status `blocked_under_13` and return a `blockedUnder13` count; the share dialogs show a warning. `users.isMinor` and age at the event date do **not** affect this. `evalShareBlocked` in `report-routes.ts` is the same rule (fail closed on error) used only to filter evals already shared to an athlete account in `GET /api/my/reports` (`dropBlockedEvalShares`) and `GET /api/my/reports/:shareId`.
   - Two separate controls: the share-to-athlete block above (age today) and the public-snapshot restriction `isEvalSnapshotRestricted` (isMinor, or no or unparseable birth date, or under 13 at the event date, or error). The second decides who may open a public link; it does not stop a coach sharing to a 13+ athlete.
   - P3d: `coppa-deletion-service.ts` step 4c deletes eval rows (`EVAL_REPORT_TYPE`) where `config.athleteId` is the athlete, in any organization (snapshots and shares cascade); `coppa-export-service.ts` adds an `evalReports` section with the full config; `profile-merge-service.ts` step 8b re-points `config.athleteId` from the source to the target user for the organization being merged, reported as `summary.evalReportsTransferred`, leaving the frozen model as saved. Covered by `tests/integration/coppa-eval-reports.test.ts`.
   - Normal user deletion intentionally keeps eval rows, as it keeps measurements: users are soft-deleted, and `config.athleteId` is not a foreign key, so nothing cascades. `loadEvalReportInputs` excludes deleted users from new reports. Whether to purge on normal deletion is a policy decision (follow-ups).
8. **PDF is rendered server-side with jsPDF** (`packages/api/utils/eval-report-pdf.ts`; `jspdf` added to `packages/api/package.json`). Server-side because the renderer draws a saved model and must serve the download route, the snapshot routes and the public PDF routes from the same code; browser-captured chart images (used by the other report types) would need a browser per report. The optional radar is drawn with jsPDF primitives (`doc.lines`, `doc.line`), not an image. The built-in Helvetica font covers only WinAnsi, so display text goes through `winAnsi`: typographic punctuation maps to ASCII and any other character prints as `?` (a non-Latin name is therefore degraded until a Unicode font is embedded). Page flow: sections are measured then placed in one loop; a gauge row is never split by a page break; only the `headline` and `retestTrend` sections may break between rows (title repeated as "(continued)", and only when at least 3 rows or 60 mm fit and at least 2 rows remain); other sections move whole to the next page. `buildEvalReportPdf` returns block positions so tests can assert the rules. Rendering dispatches on the snapshot's top-level `reportType: 'eval'` in `generatePDF`, and `sendEvalReportPdf` serves `GET`/`POST /api/reports/:id/pdf`.
9. **Load and the coach note live only in the saved report config.** There is no event-level or athlete-level store. The selection dialog pre-fills from the latest saved eval for the same event and athlete (`GET .../eval-report/defaults`, `source: "saved"`), else computed defaults. The organization separately remembers its last selection and edited presets in `org_eval_report_settings` (`lastSelection` carries no Load or note).
10. **Product decisions carried from the spec (John, 2026-10-06/08).** No placement recommendation anywhere in the report; the coach gives it verbally. The share link is off by default and is created only on request through the existing share dialog. No automatic delivery. Movement is the band word only. Radar only when the coach selects it. The old one-pager branch is superseded; AM-FEAT-018 (momentum) is not a blocker (momentum is shown when present and never compared). Templates are not stored in `reports.isTemplate` (nothing filters on it, `organizationId` is NOT NULL, and a template is a different entity); they live in `eval_battery_templates`. Athletes cannot see eval reports except through an explicit share.

## Alternatives rejected

- A new `eval_reports` table: duplicates snapshots, shares, public links, pinning, archiving and the "my reports" plumbing, and the gate list above would still exist for the new table.
- Live-only generation (no saved row): cannot be shared, snapshotted or audited, and a later correction would silently change what a family was sent.
- Reusing the individual report generator: reads timeframes and history, computes age as of today, and cannot express event scope or the Fresh & Healthy panel.
- Storing metric codes in templates and selections: a rename (as AM-FEAT-016 did) would silently break saved templates.
- Reusing `reports.isTemplate` for battery templates (see decision 10).
- Browser-captured chart images for the radar: needs a client in the loop for a server-rendered report.
- Gating by `requireRole('coach')`: it resolves the organization from the user's primary organization, which is wrong for a user who is a coach in one organization and an athlete in another.

## Consequences

### Positive
- Sharing, snapshots, public links, PDF routes and "my reports" work for eval reports with little new code, and a saved report is reproducible.
- Strict matching means the report prefers "value only" over a wrong comparison.
- Wellness data cannot reach the report: a type-check guard and a runtime schema guard both fail on it.
- Templates survive code renames for every mapped key.

### Negative
- Safety rests on a convention: every route that reads or changes reports must call the gate. A forgotten route would expose eval rows to any org member, athletes included. The access integration test (`tests/integration/eval-report-access.test.ts`) is the net.
- Eval rows are found by `config->>'athleteId'` / `config->>'eventId'`; the partial expression index `reports_eval_athlete_event_idx` (migration 0153, also in the drizzle table) covers these lookups.
- The frozen model duplicates data and is not re-derived when benchmarks change.
- Non-Latin names print as `?` in the PDF.
- The college gauge depends on D1 row naming; an unnamed or renamed row silently drops the gauge.

### Neutral
- Two separate controls decide minor handling for eval rows (share block by age today; public-link restriction by `isMinor` and age at the event date); they can disagree for one athlete by design (follow-ups).
- The gate loops are sequential awaits (`hasInaccessibleEval`, `dropBlockedEvalShares`).

## Known limitations / follow-ups

See `docs/EVAL_REPORT_FOLLOWUPS.md` for the prioritized list. Highlights: embedded Unicode font; merge-time renumbering of 0153; male benchmarks (AM-FEAT-020) and tier ladders for age-group sets; the eval Playwright spec is not in CI because the E2E suite is red (#490).

## Addendum (2026-10): managing templates

- **The server normalizes template keys.** Create and PATCH store every key as its logical key when the code has one (`FLY10_TIME` becomes `FLY_10`), using `keyForCode(resolveTemplateKey(key))`. The web knows metrics only by code, so the editor can send a code for a newly added test and the stored form stays canonical (labels, the single-leg rule and code renames keep working). Moving `TEMPLATE_METRIC_CODES` into `packages/shared` would have given the client the map too, but is a larger refactor for the same result.
- **Eligibility is checked against what is new.** Derived metrics are always rejected; missing, inactive and not-offered metrics only when new in that save. Rejecting them always would block every edit of an older template after a site admin switches a metric off or narrows its organization types.
- **Templates are copied, not linked.** Applying a template copies its tests into the event; nothing stores a template id. So edits and deletes never change existing events or reports.
- **The UI deletes instead of archiving.** Since nothing references a template, a hard delete is safe; the audit row keeps the full template. Archive stays an API-only route with no restore: a restore route and an archived list would need name-collision handling against the live-name unique index, and are out of scope.
- **Last write wins.** Two people saving the same template at once keep the later save; there is no version check.
